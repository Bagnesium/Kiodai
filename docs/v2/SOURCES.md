PM-Bench's released seven-day week was synthetically generated and validated (§3.2–3.3). We do not touch it or tune on it. Its internal task table and `compute_due_now` are evaluator/environment data. The released `run-llm` path contains an invalid-output fallback using `due_now` (`sim/pm_bench.py` near line 1947). We do **not** call that path. The previously audited iterator fixes choices before computing evaluator annotations; its model boundary receives only public text/handles/channels. The v2 controller similarly never receives a scenario object. Native completed-handle removal still prevents an independent test of prompt-driven duplicate prevention. The native scorer reports Set-F1, not ordinary percentage accuracy; ongoing A/B/C choices advance the task but are not a separate accuracy endpoint here.

PIS evaluates the released PM-Bench week with micro Set-F1 and update/cross-day diagnostics (§4). Its context/store pipeline is described in the paper, but without released code we cannot verify the precise history serialization, annotation isolation, initialization or all retry settings. Page 2 promises code upon acceptance. Its timing includes critical-path work, while Table 3's token totals explicitly exclude judge/embed side calls; we count **every** extraction, selection and validation retry. No PIS performance number is presented as a Kiodai measurement. The completion-assumption difference was checked visually against Eq.7 on PDF page 4. No claim of faithful reproduction, comparable compute, or state of the art is justified.

TriggerBench separates prospective interventions from matched retrospective questions, with synthetic blueprint/dialogue construction and sufficiency/necessity checks (§3.4–3.5). Its PM Accuracy uses an LLM judge, and Slot Match measures entity recall (§4.1); neither is our Set-F1. Its published [official repository](https://github.com/KristenZHANG/TriggerBench-Official), commit `c426163`, contains only README and says code/data will be released. These materials therefore cannot supply runnable untouched trajectories now. The existing Kiodai development story is one already-inspected trajectory; demos are narrow software cases. Consequently v2 uses four newly authored synthetic template families, three declared seeds each. All are development/exploratory, with same-process authorship and full exposure disclosed.
